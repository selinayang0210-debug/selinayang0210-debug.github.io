My design contribution

I defined the product, information architecture, collaboration rules, and interfaces: how stages organize work, how roles share responsibility, and when a proposal is allowed to change the project.

AI-assisted implementation

I used AI coding tools to help implement and iterate on those designs. This is separate from the AI inside Orbit, whose drafting and confirmation boundaries are explained below.

The starting point

Connect the work.
Make collaboration visible.

Orbit grew out of my experience collaborating on projects: discussing work in meetings, agreeing responsibilities, sharing files, and iterating on feedback. When these activities sit in separate places, teammates have to piece together who owns the work, which version is current, and what happens next.

I built Orbit around a shared project structure. Stages connect the plan to tasks; tasks connect people to files and feedback; meetings and conversations retain the reasons behind decisions. AI helps organize this information, while people keep control of changes to the work.

Each piece of work should make three things clear: who owns it, where it stands, and who takes the next step.

Information architecture

A personal way in.
A shared project underneath.

I separated workspace navigation from project navigation. A teammate can find their own work across projects, then move into one project without losing its people, stage, or history.

Organize around the work

Project → stage → task gives each piece of work a place. Files, feedback, and meeting records link back to that context instead of becoming isolated destinations.

Separate connection from access

Contacts support relationships and private conversation. Joining a project is a separate, accepted invitation. Knowing someone does not expose their other projects.

Offer more than one way back

A task can be reached from My work, a stage, a person, or an attached chat message. These entry points open the same task, preserving its identity and history.

See the plan.
Find your part in it.

Orbit supports daily teamwork as well as PM coordination. Overview shows the current stage and who is working on what. Stages makes the plan inspectable through a list, board, or timeline of the same tasks.

Make constraints visible

Scheduling uses estimates, dependencies, workdays, and co-assignee availability. Missing estimates remain unscheduled. Suggested dates appear in a preview before the team adopts them.

Give handoffs a decision point

Review progress and unresolved feedback remain visible before the PM confirms a handoff. The next stage starts without erasing the previous stage’s files, discussions, or decisions.

Shared visibility.
Explicit responsibility.

Seeing a task is different from owning, reviewing, or following it. I made those relationships explicit so teammates can understand both the current state and who can take the next action.

Assignees
Do the work

Multiple people can own the same task, edit it, and share progress and deliverables.

Reviewers
Make feedback explicit

Each reviewer approves or requests changes for themselves. Approval is distinct from task completion.

Project PM / co-PM
Coordinate the shared plan

Assign work, manage the plan, and confirm a stage handoff. The team can identify its project lead.

Followers
Stay informed

Receive relevant updates without gaining editing rights or becoming an approver.

Transparency has a scope

Project membership defines shared visibility. Private messages remain private, and avatar work cards show only projects both people belong to. Removing someone from a channel does not silently remove them from the project.

Keep the feedback
with the work it refers to.

A shared workspace needs more than a file list. Teammates need to know which version a comment refers to, which task it belongs to, and what decision followed.

A new version should not rewrite an old conversation

If a chat attachment points to version 1, uploading version 2 does not replace that attachment. The original comment still makes sense when someone returns later.

Likewise, reviewer approval and task completion stay separate. A new upload does not silently inherit the previous version’s approval.

AI boundaries

AI drafts the proposal.
People decide what changes.

Discussion often contains changes that have not reached the project plan. Orbit makes them reviewable: AI drafts, an authorized teammate checks, and the system saves the confirmed result.

What AI reads
The meeting text or project Chat content supplied for this review, plus existing project tasks and members. The user initiates the review.
What AI drafts
A Summary and pending Suggestions. The model proposes whether to create a task, edit an existing task, or record a Decision. Generating or saving a Summary applies no task change.
What people decide
Check the source, proposal type, and proposed values; edit, dismiss, or confirm. Task edits follow task permissions; confirming a Decision requires a PM or co-PM.
How uncertainty is handled
The prompt requires unsupported fields to be omitted and uncertainty explained, without inventing people, dates, or agreement. These are model instructions, not a guarantee of correct interpretation.

Checks have limits

The system checks exact source quotes, referenced tasks and members, and supported fields and values. Those checks do not prove that the quote supports the proposal, or that the model classified it correctly.

What has been verified

The meeting example below verifies one prepared transcript through a pending estimate change, human confirmation, and the saved task. It demonstrates the workflow; classification accuracy and ambiguous or mixed statements still need broader testing.

Three concepts, not three consecutive stages

Suggestion
A proposal awaiting review. It may concern a task or the project’s direction.
Decision
Confirmed team direction, kept as an independent record with its revision history.
Update
An activity entry for a saved change: a task edit, or a Decision added or revised. Decision entries link back to the original record.

After confirmation, a task proposal changes the task; a direction proposal creates an independent Decision. Both produce an Update. Decisions holds the current direction; Updates makes recent changes visible.

Decision · project direction

Turn a Suggestion
into a Decision.

Decisions answers “What has the team agreed on?” Each Decision stays as an independent, lasting record. When it is added or revised, Updates also shows a linked activity entry. Opening it returns to the current Decision; its revision history preserves earlier wording, who changed it, and when.

Changing a task field

“We all agree to move this task’s deadline to Friday.” The subject is still a task date: review a task Suggestion, then save the task change and its Update.

Recording team direction

“V1 stays email-only; defer social login.” This defines release scope: review a direction Suggestion, then confirm a Decision that the team can return to.

The distinction is what the statement changes, not simply whether it says “we agree.” These examples explain the intended distinction, not a measured classification capability. The AI review action also affects its prompt: decision extraction requests agreed direction only. People still need to check the resulting type and content.

Keep the release boundary explicit.

AI extracts “email sign-up only for V1” from the discussion. The original wording remains visible while the proposal is still pending.

IA iterations

Three decisions that
reshaped the structure.

The early prototype already contained the main features. The harder question was what should sit together, what needed its own context, and which distinctions the team should never have to infer.

01

Navigation scope

Give personal work and shared work different entry points.

The early layout put a personal updates rail beside the project overview. That asked one screen to answer both “What needs my attention?” and “Where is the team?” I gave those questions distinct homes so personal urgency would not determine the hierarchy of shared project information.

Earlier structure
Home and the project Overview coexisted; a personal rail repeated focus items and pending updates beside shared work.
Structural change
Made Home explicitly Projects, retained cross-project responsibilities in My work and Inbox, and removed the persistent personal rail from Overview. The selected project now owns its own navigation and shared context.

Trade-offPersonal updates require returning to a dedicated entry. I accepted that extra navigation to keep the project overview focused on the same shared questions for every teammate.

02

Primary organizing unit

Make the stage organize the work, not just describe progress.

The first overview was built around each person’s current focus, while stages described the project journey separately. That structure explained who was busy, but made the team reconstruct which tasks, deliverables, and unresolved feedback belonged to the same phase. I made stage context the organizing layer of Overview.

Earlier structure
A person → current focus table, with recent files and a separate stage-detail page.
Structural change
Selecting a stage now scopes its team tasks, shared work, feedback, and decisions together. Tasks became the shared records that connect these views; People and My work are alternative ways to reach the same work.

Trade-offThis adds a level between project and task. I kept direct task entry points for daily work, while stage browsing remains separate from the PM’s decision to advance the project.

03

Meaning & information states

Separate what was proposed, agreed, and actually changed.

The early Decisions area included proposed items distinguished by a status label. A discussion can contain a request, an agreement, and a later change; grouping them as decisions makes readers interpret how much authority each item carries. I made that distinction part of the information model.

Earlier structure
Proposed and agreed items appeared in the Decisions list; pending updates also lived in personal update cards.
Structural change
Suggestions holds pending proposals; Decisions preserves confirmed direction as independent records. Updates brings recent task changes and Decision additions or revisions into one activity view, with Decision entries linking back to their original records.

Trade-offThree categories take more explanation than one activity feed. I kept them in the project context so the team can distinguish agreement from execution without adding a separate AI destination.

The relationships
are the product.

The key design decision was to connect work through a stable project structure, then make responsibility, evidence, and changes visible within it. AI became useful because the relationships and decision boundaries were already clear.

What works today

A persistent workspace connects planning, co-assignment, file versions, feedback, review, and stage handoffs. The public demo gives each visitor an isolated sample project, with the same workflow on desktop and mobile.

What still needs evidence

Real-team testing still needs to check whether people can find the right version, identify the next owner, and complete a handoff. Model accuracy and repeat adoption also remain open. Multi-person calling still needs cross-network validation. No measured efficiency outcomes are claimed.
